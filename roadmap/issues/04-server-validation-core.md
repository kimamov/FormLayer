# v2: opt-in server-authoritative validation (core mechanism)

Labels: `enhancement`

Part of the roadmap tracking issue. Depends on the validation-pipeline issue. The TYPO3 transport is a separate issue.

## Goal

Mirrored client validators stay the default. Server validation is an **opt-in** layer. The core owns the mechanism (when to call, batching, pending state, cancelling, merging). The core doesn't know about any transport: adapters supply a `validate` function.

## API

```ts
createFormController(form, submitFn, {
  serverValidation: {
    mode: 'client+server',                 // 'client' (default) | 'client+server' | 'server'
    validate: ({ fields, formData, signal }) => Promise<ServerValidationResult>,
    debounceMs: 300,
  },
});

interface ServerValidationResult {
  fields: Record<string, string[]>;   // only the requested fields; [] = valid
  form?: string[];                    // form-level errors
}
```

| Mode | Client rules | Server check on blur/change |
|------|--------------|-----------------------------|
| `client` | yes | never. Server-only rules are checked on submit. |
| `client+server` | yes, first | only fields with a `server: true` rule, and only once their client rules pass |
| `server` | no | every field |

## Scope

- [ ] `serverValidation` option on `FormControllerOptions` and on the registry's `init`.
- [ ] Per-form scheduler: at most one request in flight. Fields that change during the debounce are batched into one request. A newer batch aborts the older one.
- [ ] While a request is pending, `isValidating` is set on the requested fields.
- [ ] Merge server errors with client errors. Server errors stay until the field's value changes (reuse today's server-error logic).
- [ ] Form-level errors from `result.form` go into `FormState.formErrors` (see the events/submission issue).
- [ ] Failure policy: a network error, a non-2xx response or invalid JSON leaves the client result in place, emits a `formlayer:server-validation-error` event, and **never** blocks typing or submitting.
- [ ] On submit: in `server` mode no pre-validation runs, and the submit response's errors are applied as today.
- [ ] Tests with a fake `validate` function: batching, aborting, merging, the failure policy, each mode.
- [ ] Docs: a "Server validation" guide.

## Acceptance criteria

- Blurring three fields within the debounce window sends one request listing all three.
- A slow response for an old value never overwrites the result for a newer value.
- With the transport throwing, the form still submits.

# v2: validation pipeline (context, async, typed options, messages, triggers)

Labels: `enhancement`, `breaking`

Part of the roadmap tracking issue. Depends on the field-core issue.

## Problem

- Validators only receive `(value, options)`, so they can't look at other fields (no "confirm password") and file inputs need the `__files` hack.
- Async validators are silently skipped during field validation, so a form with a failing async rule still passes.
- Options are `Record<string, unknown>`, and messages are hardcoded English.

## Scope

- [ ] New signature: `validate(value, options, ctx)`, where `ctx` = `{ field, form: { getValue(name) }, files, signal }`. Remove `__files`.
- [ ] Async is first-class:
  - `FieldState.isValidating`;
  - starting a new run aborts the previous one (through `ctx.signal`);
  - `field.validate()` returns `Promise<FieldValidationResult>`;
  - `form.validate()` awaits every field;
  - synchronous rules still give an immediate result, so the UI doesn't flicker.
- [ ] `defineValidator<Options>({ type, options: { minimum: Number, … }, validate })` converts attribute strings to the declared types.
- [ ] Message resolution order:
  1. `rule.options.message` (sent by the server);
  2. a `messages` / `t(key, params)` resolver, configurable per form or registry;
  3. a built-in English default.

  Built-in validators return message keys plus parameters.
- [ ] Triggers per field: `data-validate-on="blur|change|submit"` (default `blur`, then `change` once touched, as today). Async rules get a configurable debounce.
- [ ] Server-only rules: a rule with `"server": true`, or an unknown `type`, is skipped on the client **without a warning** and is marked for server validation (see the server-validation issue). Without server validation it is left to the submit.
- [ ] **Default trigger follows the web.dev timing guidance:** validate on blur only once the field was edited, clear errors on `input`, and validate everything on submit (C1).
- [ ] **Dependencies:** a rule that names another field (`options.field`) re-validates its field when that other field changes, if the field was touched (X2).
- [ ] **Built-in cross-field validators:** `Equals` (`field`) and `DateNotBefore` (`field`), so the playground's integrator workarounds can be deleted (X1, X3).
- [ ] **Form-level rules:** `data-validate-form` on `<form>`, with `AtLeastOne` (`fields`) as the first built-in. Results go into `FormState.formErrors` (X4).
- [ ] Per-form validator registry, with the global registry as a fallback.
- [ ] Docs: update the validators reference and add a "cross-field validator" example.

## Acceptance criteria

- A failing async rule makes `form.validate()` resolve to `false`.
- A "confirm password" validator works through `ctx.form.getValue()`.
- Typing quickly into a field with an async rule fires one request per debounce window, and outdated results are ignored.
- A `data-validate` rule `{"type":"UniqueEmail","server":true}` produces no console output.
- Playground checks C1, C6, X1, X2, X3 and X4 pass, with `playground/src/integrator/cross-field-validators.ts` deleted.

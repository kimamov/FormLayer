# TYPO3: server-validation transport and validate-only middleware branch

Labels: `enhancement`, `typo3`

Part of the roadmap tracking issue. Depends on the server-validation core issue.

## Client (`formlayer/typo3`)

- [ ] `createTypo3ServerValidation()` returns a `serverValidation.validate` function:
  - POSTs the full `FormData` to `form.action` with the headers `X-Form-Ajax: 1` and `X-Form-Validate: <field>,<field>`;
  - maps TYPO3 field identifiers to FormLayer field names, the same way `applyValidationErrors` does today.
- [ ] `initTypo3Forms({ serverValidation: { mode } })` wires it up. It is off by default.
- [ ] It only runs when the form has AJAX enabled (`data-ajax="1"`). Otherwise it falls back to `client` mode with a single debug log.

## PHP (sitepackage; spec documented in `docs/…/typo3-backend.md`)

The sitepackage code lives outside this repository. This issue covers the spec and documentation. The PHP change itself goes into the sitepackage.

- [ ] `AjaxFormSubmitMiddleware` gets a validate-only branch, used when `X-Form-Validate` is present:
  - bind `FormRuntime` exactly as today and validate the **current page**;
  - do **not** advance the page, update `__state`, render, or run finishers;
  - filter the errors to the requested fields. Errors on fields hidden by client variants are already stripped.
  - Response `200 {"fields": {"email": ["…"]}, "form": []}`. Use `400` for malformed requests, as today.
- [ ] `sitepackage:form.validationData` emits `"server": true` for TYPO3 validators that have no client equivalent (custom PHP validators, for example).
- [ ] Rate-limiting and spam considerations documented. Validate-only requests never trigger finishers or mails.

## Acceptance criteria

- In the demo setup, a custom PHP validator, for example "email not already registered", shows its error on blur in `client+server` mode.
- A validate-only request never changes the step or `__state`.
